## 優先すべき指摘

### RQ-01 / P1 / 確認した設計矛盾：未確認の「取り組み」が必須推薦根拠に入る

- 要件：F09（`REQUIREMENTS.md:31`）は「未確認の研究方法を3根拠に数えない」。F08（同30行）は取り組みを含む3種類を要求。F14（同36行）は取り組みを分野の例とし、実施課題の保証にはしない。
- 実装：`scripts/build_questions.py:78` はactivity質問すべてに「各研究室がこの方法を使う保証ではありません」と付記する。`site/engine.js:33-37` はタグ一致だけで、そのactivityを推薦根拠に採用する。研究室がその取り組みを扱うことを示す情報・検証済み状態は参照していない。出典は一律にdescriptionまたはdirectory URLであり、質問中の取り組みを直接裏付ける箇所とは結び付いていない。
- 影響：「本人がその取り組みに関心を持った」証拠はあるが、「その研究室がその関心に応える」証拠とは限らない。注記だけではF09との衝突は解消しない。
- 改善：回答根拠と研究室側の対応証拠を分ける。活動・問いごとに確認済みの研究室情報と対応箇所を持たせ、未確認のものは推薦の必須根拠に数えない。または要件自体を「分野への関心を探す例」に変更し、そのサービス上の意味を利用者に説明する必要がある。
- 限界：全activityと全研究室の実態不一致を立証したという指摘ではない。**未確認の活動でも根拠として採用される実装条件**と要件の矛盾を確認した。

### RQ-02 / P2 / 再現済み不具合：件数変更後の「任意の回答を編集」が別の質問へ飛ぶ

- 要件：F11（`REQUIREMENTS.md:33`）は結果から任意の回答を編集できること。
- 実装：`site/app.js:188-192` のeditStepは回答配列を切るだけで、編集対象回答のtargetCount・continued文脈を戻さない。`site/app.js:109` は現在のcount/keepExploringで次の質問を再選択する。正常な再開時は `site/engine.js:110-114` が回答ごとのtargetCountを使用しており、編集時との差がある。
- 再現：質問seed=123、希望20件、質問タグにgamesがある場合だけ「はい」、それ以外「いいえ」として合法な回答を作る。その後希望数を1件へ変更し「61問目から見直す」を選ぶ。選んだ61問目は `topic_mind_inquiry` だが、同じ60回答のprefixを現在のcount=1でrenderすると `topic_software_inquiry` が選ばれる。
- 文脈の失われ方：元の各回答にはtargetCount=20が保存され、この経路ではcontinued=false。結果画面でcount=1へ変更しても既存回答内のtargetCount=20は維持される。しかしeditStepは選択回答のoptionIdsだけをdraftへコピーし、その回答自体をsliceで除去する。当時のtargetCount=20とcontinued=falseを編集画面用に復元しないため、renderQuizが現在のcount=1から別質問を選ぶ。既存prefixの文脈が消去されたというより、編集対象の文脈を使わず再選択する不具合である。
- 影響：ユーザーが編集対象として指定した質問を編集できない。既存テストは保存経路の再生しか検証せず、appのeditStepと件数変更の組み合わせを検査していない。
- 改善：編集対象の質問ID・当時の分岐文脈を保持し、その質問自体を編集画面に出したうえで後続だけ再計算する。この組み合わせの回帰テストを追加する。

### RQ-03 / P2 / 部分適合：一般の関心から段階的に深掘りする順序がない

- 要件：F03（`REQUIREMENTS.md:25`）、利用の流れ（同14行）は身近な関心から理由・問い・取り組みへ進める。
- 実装：明示的な親子遷移は `site/engine.js:73-79` のculture→呪術3問だけ。ほかは情報量で同時に候補化し、interest→inquiry→activityの段階制約がない（同82-98行）。
- 再現例：seed=123、AI/software/robots関心、希望5件では、11広域質問の後、12問目software_activity、13問目software_inquiry、14問目software_interestとなる。最初に「やってみたい方法」を尋ねてからテーマ関心を尋ねており、段階的に近づく説明が実装されていない。
- 影響：入口が未形成の高校生には、突然研究活動の判断を要求する。広告的な「好きの理由をたどる」と実際の質問列が一致しない場合がある。
- 改善：各主要関心に対し、日常・作品の入口→理由→研究の問い→活動の順序または短い説明を用意する。情報量の最大化だけで順序を決めず、理解可能性を制約にする。
- 判定の限界：身近な広域入口自体はあるため、F03全面未実装ではない。現行の短い受入文では段階の定義が曖昧であり、明確化が必要。

### RQ-04 / P2 / 確認済みデータ要件不足：推薦対象外264件の理由を区別していない

- 要件：`REQUIREMENTS.md:60` は対象外264件の「理由を区別する」。
- 実装：`scripts/audit-reachability.mjs:32` は全対象外IDに同一の理由文字列を付ける（説明・タグ・URLのどれかが足りない、という選言）。実データの理由種類数は1。`scripts/build_catalog.py:135` もeligibleの真偽しか残さない。
- 影響：ある研究室がなぜ除かれたか、何を確認すれば復帰できるかが分からず、全研究室への公平な到達を広げるための修正対象を判別できない。
- 改善：不足理由をレコードごとのコード・該当元行・修復条件として保存する。「説明不十分」「テーマタグ未対応」「URL不足」などを複数保持可能にする。

### RQ-05 / P2 / 確認済み保存の制約漏れ：101件目以降が再読み込みで消える

- 要件：F18/F20（`REQUIREMENTS.md:40,42`）はブラウザー内の保存と再開。件数上限や削除規則を定義していない。
- 実装：`site/app.js:197` は上限なしでsavedへ追加し保存成功の通知を出すが、同23行は先頭100件だけを永続化、同44行も100件に制限する。保存済み一覧（同215-217行）には解除ボタンがなく、現在の結果カードにない候補を一覧から削除できない。
- 影響：繰り返し利用して101件以上を保存すると、保存成功と表示された後半候補が再読込で消える。別の探索で保存した候補は、その場で解除する経路も乏しい。
- 改善：上限を明示し、上限に達した時点で追加を止めるか、永続化できる範囲へ設計変更する。保存一覧に解除操作を設ける。今回はコード経路から確認しており101件の実UI操作はしていない。
